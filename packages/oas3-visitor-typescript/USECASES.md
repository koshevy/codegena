# TypeScript visitor use cases

Use these tables to plan and audit tests for the TypeScript visitors in
`src/visitors`. Cases are grouped by **topology**: the relationship between a
schema and its nested, sibling, or referenced schemas.

## How to read the tables

- **Case ID** names a reusable behavior, not a fixture or domain. Each ID links
  to its own anchor so reviews and issues can point to one case. A row can link
  several schemas that test the same invariant.
- **Primary visitor** links to the first visitor that handles the resulting
  transitive node. Other visitors may handle its nested nodes.
- **JSON Pointer** locates the case within its linked fixture; `#` is the
  fixture root. Broad scenarios use
  [comprehensive.jsonc](src/__fixtures__/comprehensive.jsonc) and imported
  examples in `src/__fixtures__`; focused cases use fixtures in
  `src/visitors/__fixtures__`.
- **Exact expected declaration(s)** shows a short result where practical.
  “Linked `toBe`” directs you to the assertion in the testing file. An
  expected-output link points to the complete declaration listing it compares.
- **Option profile** uses `default` when no visitor option is supplied.
  **Test level** distinguishes `visitor`, `public` (generator or parser entry
  point), and `helper` tests.
- **Output boundary** matters for exact text: visitor and helper tests compare
  the TypeScript printer's intermediate output; public and CLI tests compare
  complete files formatted after imports are assembled.
  The [publication suite](../../apps/cli-delivery-e2e/README.md#cases)
  runs the installed CLI outside the repository and compiles its full output
  under TypeScript 5, 6, and 7.
- **Expected log** records diagnostic behavior, separate from the generated
  TypeScript type. `none` describes an intended expectation; it does not
  imply that every linked test asserts the absence of a log.

### Coverage status

The status describes what the linked tests actually assert:

- `covered`: a direct assertion checks the listed behavior.
- `partial`: tests assert only part of a broader fixture or behavior.
- `gap`: no direct assertion checks the listed behavior.
- `investigate`: a fixture comment identifies behavior that remains uncertain
  or unsupported.

This inventory does not imply that tests assert every keyword in each fixture.

## When adding a row

1. Find an existing case with the same behavior and add the new fixture and
   test there. Create a new case only for a distinct invariant, and name it for
   the behavior rather than the fixture or domain. Give its case ID a unique
   anchor and link the ID to that anchor.
2. Cover the primary visitor directly, then add pairwise topology interactions
   and option boundaries that change behavior. Avoid the full Cartesian product.
   Hold the fixture constant when comparing option profiles.
3. Assert the complete declaration with `toBe`; for named references, inspect
   the complete generated listing. Add a representative TypeScript assignability
   check when text alone cannot establish exclusivity or an impossible type.
4. Assert warnings and errors when conversion loses information or cannot
   represent a schema. Mark proposed tests as `gap` or `investigate` until an
   assertion exists; a broad output snapshot alone is `partial` coverage for
   a narrower semantic invariant.
5. Check that JSON Pointers, local fixture and test links, case anchors, and
   coverage statuses remain accurate after each edit.
